1. Arquitectura de alto nivel

Cinco capas. Las flechas muestran quién le pide qué a quién.

Agente o componente con razonamiento Componente de código o datos LLM Usa el modelo de lenguaje Línea punteada: pieza opcional o servicio externo

Cómo leerlo:

  • Los agentes no verifican con el LLM: llaman a funciones (herramientas) que consultan los datos. El LLM interpreta resultados, detecta conflictos y explica.
  • La interfaz habla solo con el Supervisor. Todo lo que ocurre queda en el estado compartido y en el registro de auditoría.
  • Los datos son simulados. Cambiarlos por datos reales de una mina sería una fase posterior, y solo tocaría la capa de datos.

3. Flujo A · Planificación de una tarea

El proceso principal, de punta a punta. Los pasos verdes son humanos: el sistema recomienda, la persona decide.

Paso de un agente Decisión Paso humano Caso bloqueado Paso del Supervisor o del sistema

Detalles a tener presentes:

  • Personal y Equipo trabajan en paralelo: no dependen uno del otro.
  • Un control no bloqueante en NO CUMPLE no frena el flujo: aparece como advertencia en el plan propuesto.
  • Aunque el sistema marque todo en verde, la decisión final siempre es de una persona.

4. Flujo B · Resolución de un conflicto

Es el subproceso que justifica la orquestación: los requisitos chocan y el Supervisor busca una salida segura.

Por qué esto justifica los agentes: cada agente ve solo su parte, y ninguno puede resolver el choque por sí solo. El Supervisor combina sus resultados, propone salidas y las vuelve a verificar con código. Limitar a 2 rondas evita bucles y mantiene la demo predecible.

5. Flujo C · Verificación de un requisito

Cómo se llega a los tres estados de un control. El tercero evita que el sistema finja saber lo que no puede saber.

CUMPLE / paso humano NO CUMPLE NO VERIFICABLE

7. Contrato de datos entre agentes

Ejemplo ilustrativo; el contrato vigente es backend/app/contract.py y los estados reales del caso (EstadoRun, EstadoSistema) están en Stack y contrato. Acordarlo primero permite que cada persona trabaje en paralelo y que la integración no sea una sorpresa.

// Lo que devuelve cada agente al Supervisor, por control verificado
{
  "agente": "equipo",
  "control_id": "CC-ROCA-01",
  "estado": "NO_CUMPLE",            // CUMPLE | NO_CUMPLE | NO_VERIFICABLE
  "bloqueante": true,
  "detalle": "Perforadora en mantenimiento hasta el jueves",
  "evidencia": { "fuente": "equipos.json", "registro": "EQ-03" }
}

// Lo que consolida el Supervisor
{
  "tarea_id": "T-001",
  "controles": [ /* lista de resultados como el de arriba */ ],
  "conflictos": ["CC-ROCA-01"],
  "alternativas": [ { "descripcion": "...", "cumple_todo": true } ],
  "estado_sistema": "RECOMENDADO"   // RECOMENDADO | REQUIERE_CAMPO | BLOQUEADO
}

Los nombres de campos y los identificadores son un punto de partida. Los datos de cada control y su fuente deben marcarse como simulado o citar la norma real, para no dar una falsa sensación de rigor.
